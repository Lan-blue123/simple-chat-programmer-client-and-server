# 多进程并发聊天程序（socket + fork）

操作系统课程演示项目：**1 个服务端 + 多个客户端**，采用 TCP socket 通信，
**每接入一个客户端，服务端就 `fork()` 一个子进程专门与它通信**。

---

## 1. 功能

| 功能 | 说明 |
| --- | --- |
| 多客户端并发 | 最多 64 个客户端同时在线，互不影响 |
| 群聊 | 直接输入文字，所有人可见 |
| 私聊 | `/msg 昵称 内容`，只有目标用户能看到 |
| 在线列表 | `/list` 或 `/who` 查看当前在线用户 |
| 昵称管理 | 登录时登记昵称、查重；`/nick 新昵称` 可改名 |
| 上线/下线通知 | 有人进出聊天室时自动广播系统消息 |
| 优雅退出 | `/quit` 退出；服务端 Ctrl+C 时通知所有客户端后退出 |
| 终端彩色输出 | 时间、昵称、私聊、系统提示、错误分别用不同颜色（`CHAT_NO_COLOR=1` 可关闭）|

## 2. 架构与进程模型

```
                        +--------------------+
   客户端 A <--TCP-->    | 子进程 pid=15436   | <--+
                        +--------------------+    |
                        +--------------------+    |   socketpair    +----------------------+
   客户端 B <--TCP-->    | 子进程 pid=18720   | <--+---------------->| 主进程 pid=27156     |
                        +--------------------+    |  (AF_UNIX 全双工)|  · accept() 新连接   |
                        +--------------------+    |                 |  · 用户表 / 消息路由 |
   客户端 C <--TCP-->    | 子进程 pid=5176    | <--+                 |  · SIGCHLD 回收子进程|
                        +--------------------+                      +----------------------+
```

* **主进程**：只做 `accept()` 和集中路由。进程之间地址空间独立，所以"谁在线"这类
  全局状态只能由主进程统一维护。
* **子进程**：`fork()` 出来之后独占一条客户端连接，负责该连接的收发与渲染。
  某个客户端卡住或发来超长数据，只影响它自己的子进程，不会拖累别人。
* **IPC**：父子进程之间用 `socketpair(AF_UNIX, SOCK_STREAM)` 建立全双工控制通道，
  子进程把请求上交主进程，主进程把要投递的消息下发子进程。
* **僵尸进程**：子进程退出后由 `SIGCHLD` 处理函数里的 `waitpid(WNOHANG)` 回收，
  不会留下僵尸进程。

## 3. 通信协议

自定义二进制帧：`1 字节类型 + 2 字节长度 + 负载`。之所以要自己切帧，是因为
TCP 是字节流，一次 `write` 不保证对应一次 `read`（会短读、会粘包）。

| 类型 | 方向 | 负载 |
| --- | --- | --- |
| `FRAME_LOGIN` (1) | C→S | 昵称 |
| `FRAME_TALK` (2) | C→S | 聊天正文 |
| `FRAME_PRIVATE` (3) | C→S | `目标昵称 \t 正文` |
| `FRAME_LIST` (4) | C→S | 空 |
| `FRAME_QUIT` (5) | C→S | 空 |
| `FRAME_SAY` (6) | S→C | `时间 \t 昵称 \t 正文` |
| `FRAME_WHISPER` (7) | S→C | `时间 \t 昵称 \t 正文` |
| `FRAME_SYS` (8) | S→C | 系统提示 |
| `FRAME_ERR` (9) | S→C | 错误提示 |
| `FRAME_USERS` (10) | S→C | 昵称以 `\n` 分隔 |
| `FRAME_TEXT` (11) | 子进程→客户端 | 渲染好的一行文本 |
| `FRAME_BYE` (12) | S→C | 连接结束 |

> **GUI 客户端模式**：`FRAME_LOGIN` 的载荷如果是 `昵称\tgui`，服务端子进程就把 S→C 方向
> 改成"下发结构化帧"（SAY / WHISPER / SYS / ERR / USERS 原样转发），由客户端自己渲染；
> 不带 `\tgui` 的普通客户端仍然收到子进程渲染好的 `FRAME_TEXT`。
> 主进程会记住哪些会话是 GUI，在有人上线/下线/改名时主动给它们推最新的 `FRAME_USERS`。

## 4. 编译与运行

需要 POSIX 环境（Linux / macOS / WSL / Cygwin，Windows 原生 `cmd` 没有 `fork()`）。

```sh
make                # 生成 build/server 与 build/client

./build/server -p 8888          # 终端 1：启动服务端
./build/server -p 8888 -d       # 终端 1：带实时看板启动（推荐演示用）
./build/client -n 小明           # 终端 2：客户端 1
./build/client -n alice          # 终端 3：客户端 2
./build/client -n charlie        # 终端 4：客户端 3
```

服务端参数：`-p 端口`（默认 8888）、`-d` 打开实时看板。

### 服务端看板（`-d`）

```
 多进程聊天服务器   主进程 pid=36508   监听 0.0.0.0:8888   运行 00:05
 在线 3 / 上限 64     累计 fork 子进程 3 次     已回收 0 个     当前存活子进程 3 个
=======================================================================
 【在线会话】 一个客户端 = 一个 fork 出来的子进程
 槽位     PID 昵称               对端地址                     在线   收到   发出
 0      36288 alice              127.0.0.1:12994             00:04      3      6
 1      36290 小明               127.0.0.1:12997             00:04      2      5
=======================================================================
 【事件流】 接入 → fork → 登录 → 群聊/私聊路由 → 退出 → waitpid 回收
 13:42:52  fork  接受 127.0.0.1:12994 → fork 子进程 pid=36288（槽位 0）
 13:42:53  登录  子进程 36288 登录成功：昵称=alice（当前在线 1 人）
 13:42:54  群聊  alice: 大家好  → 广播给 3 人
 13:42:55  私聊  alice → 小明: 这句话只有你能看到
```

- 只在 stdout 是终端时启用；重定向到文件会自动退回普通日志。
- 看板模式下子进程的 stderr 被重定向到 `/dev/null`，不会把界面冲乱。
- 想在没有终端的环境里录制看板：`CHAT_DASH_FORCE=1 CHAT_DASH_NO_ALT=1 COLUMNS=120 LINES=34 ./build/server -p 8888 -d > dash.log`
  样例见 `docs/dashboard_sample.txt`。
- 窗口拉大拉小会自适应（每帧重新读取终端尺寸），中文按两格宽度对齐。

客户端参数：`-n 昵称`（必填）、`-s 服务器地址`（默认 127.0.0.1）、`-p 端口`（默认 8888）。

### 客户端命令

```
直接输入文字       群聊
/list  /who        查看在线用户
/msg 昵称 内容     私聊（/w 亦可）
/nick 新昵称       改名
/help              帮助
/quit  /exit       退出
```

## 5. 自动演示与测试

```sh
python3 scripts/demo.py         # 启动 1 服务端 + 3 客户端，自动聊天并录制输出
python3 scripts/smoke_test.py   # 协议级自动化测试（12 项断言）
```

* `demo.py` 会把服务端日志和三个客户端的屏幕输出写入 `docs/demo_transcript.txt`。
* `smoke_test.py` 覆盖：登录欢迎、上线通知、昵称查重、群聊广播、私聊隔离、
  在线列表、非法昵称拒绝、退出通知、退出后服务端仍可服务新连接。
  当前结果：**12/12 通过**。
* `docs/ps_tree.txt` 是 3 个客户端在线时 `ps -ef` 的实测进程树，
  三个子进程的 PPID 都指向主进程。

## 7. 几个值得讲的细节

1. **`read_full` / `write_full`**：`read()` 返回值小于请求长度是常态，必须循环补满，
   同时处理 `EINTR`。这是网络编程最容易出错的地方之一。
2. **fork 之后要清理描述符**：子进程继承了监听套接字和所有兄弟进程的控制通道，
   不关闭会导致端口无法释放、连接无法断开。`child_session()` 开头统一关闭。
3. **`fork` 前 `fflush(NULL)`、子进程用 `_exit()`**：避免父子进程重复刷新 stdio 缓冲区，
   导致输出重复。
4. **`SIGCHLD` + `waitpid(WNOHANG)`**：不回收子进程会积累僵尸进程。
5. **`SIGPIPE`**：对端关闭后继续 `write()` 会被 `SIGPIPE` 杀掉，用 `SIG_IGN` 忽略，
   改为通过返回值判断错误。
6. **进程 vs 线程**：本程序用进程实现并发，好处是隔离性好、不用加锁；
   代价是共享状态必须走 IPC、进程创建开销比线程大。对比见 PPT 中的对照表。
